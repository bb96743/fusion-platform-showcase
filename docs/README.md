# 文档地图与协作规则

> 这份文件解决一个问题：**多个会话并行改造时，不要写同一个文件**。
> 起因：2026-10-04 有两个会话同时在 `需求分析文档.md` 里追加章节，出现了**两个「14.17」**。

> [!NOTE]
> **本文档描述的是原开发仓库的协作规则**。本展示仓库已移除内部工具链与运行脚本
> （`_runtime/`、`_tooling/`、`_analysis/`），因此文中的命令路径仅供参考，不再可直接执行。

## 一、谁写哪个文件（硬规则）

| 文件 | 归属 | 能写什么 |
|---|---|---|
| **`需求分析文档.md`**（根目录，主文档） | **只由「总体规划会话」维护** | 阶段计划（F0~F5）、跨模块决策（D1~D5）、机制与约定（库变更、运行、协作）、进度看板、上游同步结论、事故与复盘 |
| `docs/plans/<模块>.md` | **该模块的专属会话** | 该模块的立项、数据层/后端/前端改动、菜单权限、联调回归、验收结果、未验证项 |
| `_analysis/**` | 只读历史资料 | F0 阶段的现状分析报告，不再追加 |
| `_tooling/README.md`、`fusion/README.md`、`fusion-ui-admin/README.md`、`_runtime/README.md` | 工具/使用说明 | 与代码同批维护的「怎么用」，不写项目计划 |
| `fusion/**`、`fusion-ui-admin/**` 内的文档 | 随代码 | 上游自带的框架入门文档，改造时按需更新 |

**模块会话不要往 `需求分析文档.md` 里追加 `14.x` 章节。** 需要总体规划层面记录的事（新决策、新机制、跨模块影响），
在模块文档里写清楚，然后**交给总体规划会话**去主文档落一条摘要 + 链接。

## 二、命名与编号

- 模块计划文档固定路径与文件名：`docs/plans/system.md`、`infra.md`、`bpm.md`、`report.md`、`ai.md`。
  新增模块按同样的短名加文件（例如将来上 `crm` 就加 `docs/plans/crm.md`）。
- **模块文档内部自己编号**（`## 1.`、`## 2.` …），不要用 `14.x` 这类主文档编号，避免撞号。
- 每条记录带上**日期**与**验证证据**（命令 + 数字结果），不要只写「已优化」。

## 三、开工 / 提交 / 验证清单（每个会话都照做）

> ### ⚠️ 硬规矩：**每完成一个小步骤，就用显式路径提交一次**（项目负责人 2026-10-05 定）
>
> 不要攒到「这一轮全部做完」再提交。理由不是洁癖，是三次实际教训：
> 1. **本项目的会话已被网关中断过**（后端移植那次 524/525）—— 未提交的成果会随会话丢失；
> 2. 中断后**无法回滚到中间状态**，只能整段重做或整段放弃；
> 3. 别人的会话看不到你的在制品，攒大提交会让「谁改了什么」无法追溯。
>
> **「一个小步骤」的粒度**：一个能独立说清的改动（一次上游移植 / 一个迁移 / 一处更正 / 一次重构），
> 且**它自己就能通过编译或验证**。宁可多提交几次，也不要留下一个说不清边界的巨大提交。
>
> 例外只有一种：**改动还没到能自洽的程度**（例如代码改了但编译不过）。
> 这时继续做完再提交，不要提交半成品。

**开工前**：

```powershell
git -C D:\project log --oneline -5      # 看有没有别的会话刚提交
git -C D:\project status --porcelain    # 看工作区是否干净（有别人的在制品就别动）
```

**每个小步骤做完就提交**：

```powershell
# ⚠️ 用显式路径，不要 git add -A —— 否则会把别的会话没提交完的活儿一起打包
git -C D:\project add -- <你改的文件...>
git -C D:\project status --porcelain   # 确认暂存区里**只有**你这次的改动
git -C D:\project commit -m "<type>(<scope>): <说明>"
```

**验证**（后端改动至少要跑）：

```powershell
cd D:\project\_runtime
.\verify-all.ps1                 # 构建 + 迁移状态 + 起服务 + 冒烟
.\verify-all.ps1 -SkipBuild      # 只验证（服务已构建时更快）
```

## 四、模块计划文档怎么写

复制模板：[`_模板.md`](_模板.md) → 改名为 `plans/<模块>.md`，然后按模板的 7 个小节填。
模板结构对应 `需求分析文档.md` **14.4 单模块改造标准循环（SOP）**，不要另起一套。

## 五、与上游的关系

上游同步（看有没有值得摘的新提交）由**总体规划会话**负责，机制与本次盘点见 `需求分析文档.md` **14.19**，
工具是 `_runtime\upstream-sync.ps1`。模块会话若判断某条上游修复与自己的模块相关，
在模块文档里写「建议摘取 上游 `<sha>`」，由总体规划会话排期。
